## What Is IA-32
Intel IA-32 (Intel Architecture, 32-bit) is a 32-bit instruction set architecture introduced by Intel with the 80386 processor in 1985. It extended the earlier 16-bit x86 architecture to support 32-bit registers, memory addressing, and arithmetic operations, enabling more powerful and efficient computing. IA-32 uses a segmented memory model, supports both real and protected modes, and forms the foundation for most modern desktop and server processors, including later x86-64 architectures that maintain backward compatibility.

### General Format
The general format of 80836 Instructions is:

      +---------------+---------------+---------------+---------------+
      |  INSTRUCTION  |   ADDRESS-    |    OPERAND-   |   SEGMENT     |
      |    PREFIX     |  SIZE PREFIX  |  SIZE PREFIX  |   OVERRIDE    |
      |---------------+---------------+---------------+---------------|
      |     0 OR 1         0 OR 1           0 OR 1         0 OR 1     |
      |- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -|
      |                        NUMBER OF BYTES                        |
      +---------------------------------------------------------------+

      +----------+-----------+-------+------------------+-------------+
      |  OPCODE  |  MODR/M   |  SIB  |   DISPLACEMENT   |  IMMEDIATE  |
      |          |           |       |                  |             |
      |----------+-----------+-------+------------------+-------------|
      |  1 OR 2     0 OR 1    0 OR 1      0,1,2 OR 4       0,1,2 OR 4 |
      |- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -|
      |                        NUMBER OF BYTES                        |
      +---------------------------------------------------------------+
[Figure 17-1.  80386 Instruction Format]

The names of these fields can be quite confusing, but don’t worry, we’ll soon learn what each of them represents. At least we can observe that, apart from the opcode which always appears (1 OR 2 bytes), the other fields may be absent (0 bytes), and some fields do not have a fixed length (opcode can be 1 or 2 bytes, displacement and immediate can be 1/2/4 bytes).

For any given instruction in its binary form, the boundaries of its fields can be clearly determined without ambiguity.

For example:

`100017:	66 c7 84 99 00 e0 ff ff 01 00  	movw   $0x1,-0x2000(%ecx,%ebx,4)`

The interpretation is as follows:

      +---------------+---------------+---------------+---------------+
      |  INSTRUCTION  |   ADDRESS-    |    OPERAND-   |   SEGMENT     |
      |    PREFIX     |  SIZE PREFIX  |  SIZE PREFIX  |   OVERRIDE    |
      |---------------+---------------+---------------+---------------|
      |      -        |       -       |      66       |       -       |
      +---------------------------------------------------------------+

      +----------+-----------+-------+------------------+-------------+
      |  OPCODE  |  MODR/M   |  SIB  |   DISPLACEMENT   |  IMMEDIATE  |
      |          |           |       |                  |             |
      |----------+-----------+-------+------------------+-------------|
      |    c7          84        99       00 e0 ff ff        01 00    | 
      +---------------------------------------------------------------+

<details>
<summary> Q: Why can this instruction be decoded accurately without ambiguity? Why do we know that C7 is the opcode rather than a prefix? </summary>

> **A:** There are three main reasons:
> 
> **Prefixes have fixed and non-overlapping value ranges.**
> The possible prefix values are limited and predefined, and they never overlap with opcode values.
> Moreover, each type of prefix has its own unique range.
> Therefore, once the decoder encounters the first byte not belonging to the prefix table, it knows the prefix sequence has ended and the opcode begins.
> 
> **Each opcode byte is explicitly defined.**
> Intel specifies, for every opcode, the exact structure of the following bytes — including whether a ModR/M, SIB, displacement, or immediate field should appear.
> Once the decoder recognizes the opcode (for example, `C7` = `MOV r/m16/32, imm16/32`), it immediately knows how to interpret the remaining bytes.
> 
> **The decoding process itself eliminates ambiguity.**
> Although the x86 instruction set is complex, its decoding follows a step-by-step deterministic process:
> 
> 1. Check prefixes -> Identify them if valid; stop when a non-prefix byte appears.  
> 2. Read the opcode -> Consult the opcode table for the instruction format.  
> 3. If a ModR/M byte is required -> Decode it next.  
> 4. If ModR/M indicates SIB or displacement -> Parse them sequentially.  
> 5. If the instruction specifies an immediate -> Fetch it last.
> 
> 
> Each step defines what comes next, ensuring that no bit sequence can be interpreted in more than one valid way.

</details>

<details>
<summary> Q: Why isn’t the opcode length fixed? How do we determine how many bytes an opcode has? </summary>

> **A:** In the earliest x86 processors (like the 8086), the opcode occupied only one byte, allowing for only 256 possible combinations. However, as the x86 architecture evolved, introducing more complex addressing modes, floating-point operations, conditional jumps, and instruction extensions such as `SSE` and `AVX`, a single byte was no longer sufficient to encode all instruction forms.
> 
> To solve this, Intel introduced an escape mechanism (known as an escape code). When the CPU encounters a specific byte (for example, `0x0F`), it does not immediately execute the corresponding operation. Instead, it treats this byte as an escape indicator, meaning:
> 
>> “This instruction’s opcode is longer than one byte; more bytes must be read to determine the exact instruction.”
> 
> The most classic example is the two-byte escape code (0x0F). When the CPU reads 0x0F, it knows that this marks the beginning of a two-byte opcode, and the second byte specifies the actual instruction.
> For example, the opcode for `POP FS` (Pop top of stack into FS; increment stack pointer) is `0F A1`.
> 
> In addition to using escape codes to extend the opcode space, x86 employs another mechanism:
> part of the ModR/M byte (specifically, the reg/opcode field) following the opcode can also serve as an extension of the opcode, helping to distinguish > between multiple instructions that share the same base opcode. We'll look into this later.

</details>

### Details about All Fields

In this section, we have a detailed explanation of each encoding field in the general instruction format.

#### `Instruction Prefix`
The Instruction Prefixes (also called Lock/Repeat prefixes) modify how certain instructions are executed.

| Prefix       | Mnemonic                 | Meaning                                                                                         |
| ------------ | ------------------------ | ----------------------------------------------------------------------------------------------- |
|  F0h         |  LOCK                    | Enforces atomicity for the following memory operation                                           |
|  F3h         |  REP, REPE, or REPZ      | Repeats a string instruction while a condition holds or until the count reaches zero            |
|  F2h         |  REPNE or REPNZ          | Repeats a string instruction while a condition does *not* hold and until the count reaches zero |

1. `LOCK` Prefix (`F0h`)
The LOCK prefix is used to ensure atomic operations on shared memory in multiprocessor systems.
When a memory operation is prefixed with `LOCK`, the processor guarantees that no other processor or bus master can access the affected memory location until the operation completes.

      - It applies only to instructions that perform a read–modify–write on memory (e.g., `INC`, `DEC`, `ADD`, `XOR`, `XCHG`).

      - It is ignored for instructions that do not access memory or operate only on registers.

      Example: `LOCK ADD [mem], EAX    ; Atomically add EAX to the memory location`

2. `REP`, `REPE/REPZ`, `REPNE/REPNZ` Prefixes (`F3h`, `F2h`)
These prefixes are used only with string instructions. They instruct the CPU to repeat the operation multiple times automatically, using the `CX` / `ECX` / `RCX` register as a counter.
      | Prefix                  | Full name                           | Condition for repetition                                     |
      | ----------------------- | ----------------------------------- | ------------------------------------------------------------ |
      | REP / REPE / REPZ (F3h) | *Repeat while Equal / Zero*         | Repeats until the counter = 0 **or** condition (ZF=0) fails  |
      | REPNE / REPNZ (F2h)     | *Repeat while Not Equal / Not Zero* | Repeats until the counter = 0 **or** condition (ZF=1) occurs |

#### `Operand-Size Prefix` and `Address-Size Prefix`

x86 is a variable-length instruction set.  
Depending on the current operating mode, the CPU interprets instruction operands and addresses with different default bit widths.

| Mode | Default Operand Size | Default Address Size |
|------|----------------------|----------------------|
| 16-bit Real Mode | 16 bits | 16 bits |
| 32-bit Protected Mode | 32 bits | 32 bits |
| 64-bit Long Mode | 32 bits (for most instructions) | 64 bits |

To maintain compatibility with older programs and to allow special access within the same mode, x86 introduces two prefix bytes `66h` and `67h` to temporarily override these defaults.

<details>
<summary> Q: What is operating mode? </summary>

> **A:** The operating mode specifies the “execution environment” of the CPU, including how it views memory, handles privileges, and decodes instructions.
> 
> Modern x86 processors support three primary operating modes:

| Mode | Bit Width | Introduced In | Key Characteristics | Typical Usage |
|------|------------|----------------|----------------------|----------------|
| **Real Mode** | 16-bit | Intel 8086 (1978) | No memory protection or multitasking; 20-bit segmented addressing (`segment:offset` → 1 MB range) | Legacy DOS programs, BIOS, and system startup |
| **Protected Mode** | 32-bit | Intel 80286 / 80386 | Supports segmentation and paging, privilege levels (ring 0–3), and virtual memory | 32-bit operating systems (e.g., early Windows, Linux) |
| **Long Mode** | 64-bit | AMD64 (2003) | Flat 64-bit linear addressing, expanded register set, minimal segmentation | Modern 64-bit operating systems |

> When the CPU powers on, it always starts in Real Mode (for backward compatibility with 8086). Operating systems then switch the processor into a more > advanced mode: 
> 
> `Real Mode  →  Protected Mode  →  Long Mode`
> 
> - Real -> Protected: Enabled by setting the PE (Protection Enable) bit in CR0.
> - Protected -> Long: Enabled by setting LME (Long Mode Enable) in EFER and activating paging.

</details>



#### Operand-Size Override Prefix (`66h`) ####

The Operand-Size Override Prefix changes the *operand size* of an instruction.  
It tells the CPU:

> “Use the opposite operand size from the default for this mode.”

| Current Mode | Default Operand Size | With `66h` Prefix |
|---------------|----------------------|-------------------|
| 16-bit mode | 16 bits | 32 bits |
| 32-bit mode | 32 bits | 16 bits |
| 64-bit mode | 32 bits (default) | 16 bits (or 32 bits with `REX.W` = 1) |

Example (32-bit Mode)

```asm
MOV EAX, EBX      ; Default 32-bit operands → 89 D8
MOV AX, BX        ; 16-bit operands → assembler adds 66h prefix → 66 89 D8
```
#### Address-Size Override Prefix (`67h`) ####
Similarly, the Address-Size Override Prefix changes the *address size* used for memory operands.
It tells the CPU:

> “Use address registers of the opposite width from the default for this mode.”

| Current Mode | Default Address Size | With `67h` Prefix |
| ------------ | -------------------- | ----------------- |
| 16-bit mode  | 16 bits              | 32 bits           |
| 32-bit mode  | 32 bits              | 16 bits           |
| 64-bit mode  | 64 bits              | 32 bits           |

Example (32-bit Mode)
```asm
MOV EAX, [EBX]    ; Default 32-bit addressing → 8B 03
MOV AX, [BX]      ; 16-bit operand and address → 66h + 67h prefixes → 67 66 8B 07
```
#### Combinations of Defaults and Overrides ####

The following table (Intel Manual Table 17-1) shows the effective operand and address sizes based on the **D-bit** (default attribute in the code segment descriptor) and the presence of prefixes:

| Segment Default D-bit      | 0  | 0  | 0  | 0  | 1  | 1  | 1  | 1  |
| -------------------------- | -- | -- | -- | -- | -- | -- | -- | -- |
| Operand-Size Prefix 66h    | N  | N  | Y  | Y  | N  | N  | Y  | Y  |
| Address-Size Prefix 67h    | N  | Y  | N  | Y  | N  | Y  | N  | Y  |
| Effective Operand Size     | 16 | 16 | 32 | 32 | 32 | 32 | 16 | 16 |
| Effective Address Size     | 16 | 32 | 16 | 32 | 32 | 16 | 32 | 16 |

*Y = prefix present, N = prefix not present*

#### Address-Size Attribute for Stack ####

Some instructions implicitly use the stack pointer, such as:

```asm
PUSH EAX   ; ESP ← ESP - 4, then [ESP] ← EAX
POP  EAX   ; EAX ← [ESP], then ESP ← ESP + 4
```
These instructions access the top of the stack, whose address is determined by either the SP (16-bit) or ESP (32-bit) register.
The choice between SP and ESP (the Stack Address-Size Attribut) is controlled by the **B-bit** in the **SS (Stack Segment) descriptor**.

| B-bit | Stack Pointer | Stack Address Size |
| ----- | ------------- | ------------------ |
| 0     | SP            | 16-bit             |
| 1     | ESP           | 32-bit             |

Therefore:

- For ordinary instructions, the address-size attribute is determined by the **D-bit** of the code segment and may be temporarily overridden by the **67h prefix**.

- For stack instructions (PUSH, POP, CALL, RET, etc.), the stack address size is implicit and controlled by the **B-bit** of the SS descriptor, not by the D-bit or 67h prefix.

<details>
<summary> Q: What are D-bit and B-bit? Who set them? </summary>

> **A:** In the x86 architecture, each segment descriptor (in the Global Descriptor Table or Local Descriptor Table) contains a D/B bit field.
> 
> This single bit has two different meanings depending on the type of segment:
> 
| Segment Type           | Bit Name  | Full Name              | Controls                                                                                                     |
| ---------------------- | --------- | ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| **Code Segment (CS)**  | **D-bit** | Default Operation Size | The *default operand and address size* (16-bit or 32-bit) for instructions fetched from this segment         |
| **Stack Segment (SS)** | **B-bit** | Big (Stack) Bit        | The *default stack pointer size* (SP or ESP) used by stack instructions such as `PUSH`, `POP`, `CALL`, `RET` |
> 
> Although both are stored in the same physical position (bit 54 in the descriptor), their meaning depends on whether the segment is a code or data/> stack segment.
> 
> ```asm
> 63                        32 31                        0
> +------------------------------------------------------+
> | Base[31:24] | G | D/B | 0 | AVL | Limit[19:16] | ... |
> +------------------------------------------------------+
> | Base[23:0]                     | Limit[15:0]         |
> +------------------------------------------------------+
> 
> ```
> *For code segments -> this bit is the D-bit (Default operation size), for data/stack segments -> this bit is the B-bit (Big bit)*
> 
> These bits are part of the segment descriptor, which is defined by the operating system or system-level software (e.g., during boot or context > switching).
> 
> When a segment selector is loaded into CS or SS, the processor automatically reads the corresponding descriptor from the GDT/LDT and loads the D/B bit > into its internal state.
> 
> For example:
> 
> - During OS initialization, the kernel builds GDT entries for each segment.
> 
> - The 32-bit kernel code segment has D=1 (so instructions default to 32-bit).
> 
> - The stack segment has B=1 (so ESP is used instead of SP).
> 
> - In 16-bit mode (e.g., BIOS), both bits are typically 0.
</details>

#### `Segment Override Prefix`

Segment Override Prefixes explicitly tell the CPU which segment register to use for memory addressing, overriding the default segment selection rules.

Early x86 processors (such as the 8086) used segmented addressing to access more than 64 KB of memory with 16-bit registers.

A physical address was computed as:
```java
Physical Address = Segment_Base × 16 + Offset
```
For example:
```asm
MOV AX, [BX]
; it actually means:
MOV AX, DS:[BX]
```
That is, the memory operand `[BX]` is located at an offset given by `BX` within the Data Segment (DS).

When an instruction references memory without specifying a segment register, the CPU automatically chooses one based on the addressing mode:

| Addressing Register(s) Used                      | Default Segment                     |
| ------------------------------------------------ | ----------------------------------- |
| `BX`, `SI`, `DI`, or general register indirect   | **DS**                              |
| `BP`, `SP`                                       | **SS**                              |
| Instruction fetches                              | **CS**                              |
| String operations (e.g., `MOVS`, `LODS`, `STOS`) | Source: **DS**, Destination: **ES** |

Example:
```asm
MOV AX, [BX]   ; Uses DS:[BX]
MOV AX, [BP]   ; Uses SS:[BP]
```

Sometimes a programmer needs to access memory through a different segment than the default one. For example, to read data from a different area, or in modern systems, to access thread-local storage (TLS) or per-CPU data.

In such cases, a Segment Override Prefix can be used to explicitly specify the segment register.

| Prefix (Hex) | Segment Register Used | Example           |
| ------------ | --------------------- | ----------------- |
| `26h`        | ES                    | `MOV AX, ES:[BX]` |
| `2Eh`        | CS                    | `MOV AX, CS:[BX]` |
| `36h`        | SS                    | `MOV AX, SS:[BX]` |
| `3Eh`        | DS                    | `MOV AX, DS:[BX]` |
| `64h`        | FS                    | `MOV AX, FS:[BX]` |
| `65h`        | GS                    | `MOV AX, GS:[BX]` |

Example:
```asm
MOV AX, ES:[BX] ; 26 8B 07
```
It means: Load AX from the address [BX] in the ES segment, not DS.

#### `ModR/M` and `SIB` Bytes

ModR/M and SIB (Scale-Index-Base) Bytes specify:

- Which registers are used,

- What kind of addressing mode is applied,

- Whether displacement bytes (immediate address offsets) follow.

#### `ModR/M` Byte ####

The ModR/M byte immediately follows the opcode in most instructions that involve registers or memory operands.

```asm
ModR/M byte
7    6    5    4    3    2    1    0
+--------+-------------+-------------+
|  mod   | reg/opcode  |     r/m     |
+--------+-------------+-------------+
```
- **mod**: Determines the addressing mode — whether the operand is in a register or in memory, and whether a displacement follows (none, 8-bit, or 32-bit).
- **reg/opcode**: Specifies either: (a) a register operand, or (b) extra opcode bits to extend the instruction encoding.
- **r/m**: Selects a register or memory addressing form, often combined with mod to describe how to compute the effective address.

**mod (bits 7-6):**

| mod   | Meaning                                 | Displacement Size                                    |
| ----- | --------------------------------------- | ---------------------------------------------------- |
| `00`  | Register indirect                       | none (except when r/m=101 → disp32 absolute address) |
| `01`  | Register indirect + 8-bit displacement  | disp8                                                |
| `10`  | Register indirect + 32-bit displacement | disp32                                               |
| `11`  | Register-direct addressing              | no memory access (register-to-register only)         |

**reg/opcode (bits 5-3):**
- For most instructions, it identifies the register operand (e.g., source or destination).

      Example: in `MOV r/m32, r32`, the reg field is the source register.

      General-Purpose Register Encodings：

      | Binary Code         | 000 | 001 | 010 | 011 | 100 | 101 | 110 | 111 |
      | ------------------- | --- | --- | --- | --- | --- | --- | --- | --- |
      | **8-bit Register**  | AL  | CL  | DL  | BL  | AH  | CH  | DH  | BH  |
      | **16-bit Register** | AX  | CX  | DX  | BX  | SP  | BP  | SI  | DI  |
      | **32-bit Register** | EAX | ECX | EDX | EBX | ESP | EBP | ESI | EDI |

- For “group” instructions (like TEST, IMUL, NOT, INC, etc.), it acts as extended opcode bits that specify which operation variant to perform.

      Example: Group 3 (`F6 /r` for byte operations):

      | Opcode  | `/digit` | Operation       |
      | ------- | -------- | --------------- |
      | `F6 /0` | `/0`     | TEST r/m8, imm8 |
      | `F6 /2` | `/2`     | NOT r/m8        |
      | `F6 /3` | `/3`     | NEG r/m8        |

**r/m (bits 2-0):**

The r/m field (bits 2–0) identifies:

- A register (if `mod=11`)

- A memory addressing mode (if `mod != 11`)

When the r/m field is in memory addressing mode, there are multiple possible addressing modes. For detailed information, refer to Table 17-3.

Note that `r/m = 100 && mod != 11` means to use SIB byte, and `r/m = 101 && mod == 00` means disp32.

#### `SIB` Byte ####

The SIB byte is used only in 32-bit or 64-bit addressing modes when a more complex address computation is needed, such as [base + index * scale + displacement].

The presence of the SIB byte is indicated by **ModR/M**: `r/m = 100b` and `mod != 11`.

```asm
SIB (scale index base) byte
7    6    5    4    3    2    1    0
+--------+-------------+-------------+
|   ss   |    index    |    base     |
+--------+-------------+-------------+
```
- **ss**: Scale factor (00=×1, 01=×2, 10=×4, 11=×8)
- **index**: Index register used in scaled addressing
- **base**: Base register used in the address computation

For example:
```java
Address = [EBP + ESI*4 + 8]
// ss = 10 (x4)
// index = ESI
// base = EBP
```

### Summary of Instruction Format
Now we've learnt all fields, let's look back at the first instruction in our example:

`100017:	66 c7 84 99 00 e0 ff ff 01 00  	movw   $0x1,-0x2000(%ecx,%ebx,4)`

1. **Prefix** and **Opcode**

      We know `66` is operand-size prefix, and `c7` is opcode for `MOV r/m16,imm16` or `MOV r/m32,imm32`. With the operand-size prefix it should be the 16-bit one. So we know our operand is a 16-bit immediate (`imm16`). And we need to look at the `ModR/M` byte for `r/m16`.

2. **ModR/M** (`84`):
      - `mod=10`: r/m use 32-bit displacement.
      - `reg=000`: not used.
      - `r/m=100`: SIB byte is present, so we need to check the next byte for addressing.
3. **SIB** (`99`):
      - `ss=10`: scale = 4
      - `index=011`: EBX
      - `base=001`: ECX

      Therefore the address = `[base + index * scale + disp32]` = `[ECX + EBX * 4 + (-0x2000)]`
4. **Displacement** (`00 e0 ff ff`):
      From ModR/M we know it's 32-bit displacement, so it's the 4 bytes after SBI. 

      Little-endian -> `00 e0 ff ff` = `0xffffe000` = `-0x2000`.
5. **Immediate** (`01 00`):
      From opcode we know it's imm16 so it's the last 2 bytes.

      Little-endian -> `01 00` = `0x0001` = `0x1`.
6. Together, the instruction is `movw   $0x1,-0x2000(%ecx,%ebx,4)`.
